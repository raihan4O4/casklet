# ADR 0039: Optional local application icons

Status: accepted by the user's application-icon request, 2026-10-24.

## Decision

Show actual application icons in the main Installations inventory and the Cask's Your applications list. Windows installations use the exact uninstall registration's DisplayIcon path and optional resource index. Portable applications use their stored executable path, resolved by installation ID through the existing metadata-only application query. WinGet presentation retains the observed Windows installation's icon when available. Missing, invalid, inaccessible or unsupported icon sources keep the existing package/link fallback. Display names are never used to guess identity or download artwork.

Icons are optional desktop presentation data, separate from the shared inventory DTOs and all ownership, execution and cleanup behavior. The Svelte component requests icons only near the viewport, batches up to 16 requests, coalesces duplicates, serializes extraction batches and caches results for five minutes (up to 1,000 entries per window). List loading never waits for icons. Source changes and unmounted rows ignore stale results. Decorative images retain the adjacent application's text as the accessible name.

The repository forbids unsafe Rust. A small bundled Windows C++ helper uses native resource extraction and GDI+ PNG encoding, launched with structured arguments and no visible console. This avoids weakening Rust's safety policy or adding an icon framework. Registry requests are restricted to the four supported uninstall-registration views; portable requests accept an installation ID rather than a caller-supplied file path. Icon sources must be local drive paths with EXE, DLL or ICO extensions. The helper does not execute target files, recursively enumerate directories or compute sizes/hashes. The October 24 fallback extension permits at most 64 immediate directory entries when explicit icon metadata is unavailable; this optional work remains outside inventory/Cask loading. Output is restricted to PNG data, capped in both processes; a four-second timeout kills a stalled helper. Non-Windows builds retain the fallback.

The helper is compiled by the existing MSVC build toolchain and explicitly included in Tauri bundle resources. The CSP permits image data URLs for locally extracted PNGs; script and connection policies are unchanged. This changes no schema, domain contract, cleanup capability or application authority. Registered icons can be stale or absent; this is an expected fallback, not an inventory failure.

## Validation

All 94 frontend tests pass, including batching, deduplication, caching, extraction failure, image decode failure and stale row results. Both targeted Rust tests pass: accepted registry sources and native PNG extraction with preserved missing-source positions. Svelte checks, ESLint, formatting, strict desktop Clippy, the production frontend build and the native desktop build pass. Native checks verify real Chrome association/rendering, installed icons including Photoshop and Creative Cloud, light/dark appearance, and missing-icon fallback using isolated development data, with no page errors. Four screenshots and the result JSON are retained under `.jury/application-icons/native`.

## Missing-icon and association-search follow-up

The first resolver used DisplayIcon only. A read-only local inventory check found 33 of 106 visible registrations missing that property, and the original helper extracted 72 icons. Windows Installer can publish its primary icon separately through [MsiGetProductInfo ProductIcon](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msigetproductinfoa). The resolver now tries DisplayIcon, the MSI product icon for that exact product GUID, then a single eligible executable in the registered installation folder. An explicit local uninstall executable may provide the containing folder when InstallLocation is absent; the uninstall command is never executed and its own icon is never used as an application-logo substitute. Ambiguous executables, unsupported/network paths and directories exceeding 64 immediate entries retain the fallback. No recursion or content-size calculation occurs. Invalid resource indices can fall back to the file's first icon; indirect local resource prefixes are supported.

The same ApplicationIcon component now appears beside installed-application association search results. Stable source-key cache sharing, lazy loading, decorative semantics and failed-icon fallback are unchanged. No schema, domain query, association/ownership or uninstall permission changes are involved.

On the same local inventory, 86 of 106 registrations now resolve icons, an increase of 14, including Blender, Epic Games Launcher, Bonjour and iTunes. This is a local coverage observation, not a guarantee for every Windows registration. Services, support components, absent/stale metadata and ambiguous sources can legitimately retain generic icons.

All 101 frontend tests pass, including a real image result in the association picker while pending size measurement remains non-blocking. Three targeted Rust/native icon tests pass; the disposable native fixture covers absent/broken DisplayIcon, invalid resource indices, uninstall-folder metadata, ambiguous executables and bounded enumeration. Strict desktop Clippy, type/lint/format checks and frontend/native builds pass. An isolated native Blender search verifies decoded identical PNGs in Installations and association results in light/dark modes, with no page errors. Evidence: `.jury/icon-fallback/native`; coverage observations are stored in `target/icon-coverage-before.json` and `target/icon-coverage-final.json`. Tests inspect or copy resource fixtures only; they do not run application executables or modify installed applications.
