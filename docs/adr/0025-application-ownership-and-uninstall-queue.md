# ADR 0025 - Application ownership and the uninstall queue

Status: Accepted for the October 6 application-lifecycle request.

## Decision

Install Application and Associate Existing App remain separate application-core operations. A completed MSI install with its durable absent-before ProductCode baseline gains ownership. A process-tree-completed EXE install with one new, matching, currently unchanged Windows registration gains ownership in the same SQLite transaction that registers its application association and confirms the installer operation. No existing-app association call is used to establish ownership. Ambiguous, failed, interrupted, reboot-required and preexisting results remain unresolved; names or executable locations never grant authority.

Schema 16 extends the existing managed installation records and application cleanup journal rather than introducing another lifecycle service. Historical `managed_msi_installations`, `MsiRepository`, and `MsiCleanupPlan` names remain for compatibility; they now carry MSI and supported registered EXE installations. An owner links the stable installation ID and Cask ID to the installation operation, artifact/source, immutable registration snapshot, evidence digest, installation status and, for direct EXE uninstall, the captured executable digest. Existing application associations remain references. Old informational installed-for-Cask provenance is not promoted into uninstall authority.

Applications presents Casklet-owned versus Reference from persistent removal authority. Owned Remove opens an inspectable plan limited to that installation. Reference Remove link only detaches the association. Application cleanup includes references and owners, detaches references first, then executes owned uninstalls sequentially under the existing global provider-mutation lock. MSI uses system msiexec with typed `/x ProductCode /norestart`, including MSI registrations produced by an EXE bootstrapper. Direct EXE uninstall uses the exact local absolute executable and argument tail captured in UninstallString; a fixed PowerShell helper passes those as environment data to Start-Process with visible RunAs and process-tree waiting. Registry text is never evaluated as shell code. Unquoted paths with spaces, network paths, shell/interpreter commands, missing mechanisms, links/reparse points, changed bytes, changed registrations and shared installations are preserved.

Each plan includes identity, evidence, executable digest and action in its hash. Approval and execution revalidate current authority. Intent is durable before external launch; success requires exit zero and disappearance of the exact registration. Only verified success retires ownership and the association, retaining historical journal records. A completed nonzero exit records FAILED, retains ownership and permits the next queued uninstall. An uncertain process failure, timeout, reboot result or interruption records UNKNOWN and stops further launches. Both require inspection and preserved closure before a fresh reviewed retry preview. Unstarted owners remain registered. The GUI polls durable step state for Waiting, Uninstalling, Uninstalled, Failed and Reference / Detached results.

Whole Cask removal uses this application stage before file cleanup and the existing final empty-Cask dependency check. Failed, preserved, shared or unresolved owners block removal; the Cask is not deleted while their lifecycle is unresolved. Explicit Keep installed and detach remains a separately confirmed opt-out. Existing portable and WinGet provider workflows and build capability gates remain in place.

## Migration and recovery

Startup backs up older databases through the existing migration sequence. Migration 16 adds immutable registration/executable evidence, permits reference-detach steps in the existing journal, and closes unexecuted previews because plan hashing changed. Executing and partial journals remain inspectable and closable without replay. Existing MSI evidence digests remain stable: MSI uninstall strings are not included in registry hashing because typed ProductCode is the mechanism. Manifests and recovered associations remain informational and cannot recreate uninstall authority.

## Validation and limits

Tests cover persistent EXE install-to-owned registration-to-approved uninstall, unchanged MSI ownership, manual association preservation, mixed reference/MSI/EXE queues, per-application scope, retained failures and retries, interruption stopping later launches, migration backups, tampered evidence, shared preservation and GUI removal routing. Native parsing tests reject shell commands and ambiguous executable paths. Fixture tests do not install or uninstall real third-party applications.

Windows registration disappearance verifies the registered installation, not complete removal of every file or service a third-party uninstaller may leave behind. Arbitrary EXE installers without an identifiable registration or supported safe uninstall mechanism remain visible for review and preservation; no guarantee of universal arbitrary-installer cleanup is claimed. Real Windows UAC, third-party MSI/EXE, self-deleting uninstallers, reboot and clean-machine validation remain release gates.

Research: [Microsoft uninstall registration properties](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key), [msiexec](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/msiexec), and [Start-Process argument passing, elevation and descendant waiting](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process).

## Per-user registry aliases found during integration

Windows maps both architecture views of HKCU Software uninstall keys to the same physical key ([Microsoft WOW64 registry-key rules](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys)). Native testing exposed duplicate observations that prevented one new per-user installer from gaining ownership. Keep both existing stable inventory IDs and their evidence; do not rewrite old references or ownership records. Correlation prefers the 64-bit observation only when the exact shared user key and all captured registration values agree. A baseline observation in either view proves the key preexisted, even when its metadata changes. Machine-view registrations remain distinct; mismatched, malformed or changed evidence remains ambiguous.

Claims and cleanup dependency checks include alternate-view associations/owners. Cleanup resolves the originally owned ID, revalidates all alias evidence, and requires disappearance through both views before success. A cross-Cask reference through either view blocks uninstall, including one added after approval. This extends existing plan revalidation without a new schema or ownership inference from a name/path. The application layer reuses the existing serde_json parser to compare captured data; Windows API access stays in infrastructure.

Additional regressions cover real shared HKCU fixture keys with exact cleanup, MSI/EXE alias ownership and one uninstall, changed/preexisting aliases, claim races, reference protection after approval, and retained ownership when a surviving alias prevents verification.

## October 11 reinstallation refinement

A verified new installation can reuse a stable Windows identity from a REMOVED or RELEASED ownership record. The existing atomic claim refreshes that retired row with the new operation and immutable evidence, preserving prior installer and cleanup journals. Active ownership remains protected. Completed successful reviews may retry the same claim automatically after current-evidence validation, without executing the installer again. See docs/engineering/installer-reinstallation.md.
