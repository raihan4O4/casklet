# Milestone 5 — Inventory export and manifest recovery

## Commands

```text
casklet export <cask-id> <output.json>
casklet export <cask-id> <output.md> --format markdown
casklet export <cask-id> <output.json> --machine
casklet manifest preview <path-to-manifest.json>
casklet manifest recover <path-to-manifest.json>
casklet manifest scan
casklet manifest recover-all
```

The default portable profile omits absolute paths, Cask and Resource IDs, and the managed storage root. Internal resources may include a relative path under `content`. The machine profile explicitly includes local IDs and paths. Both profiles contain names and categories, so users should review an export before sharing it. The JSON schema is `docs/schemas/inventory-v1.schema.json`; schema version is independent of the application version. Unknown fields in version 1 are ignored on read; unknown versions are rejected. Exports are informational and cannot authorize cleanup.

## Recovery boundary

Recovery requires a UTF-8 version 1 manifest no larger than 16 MiB, a matching SHA-256 sidecar, valid IDs and enum codes, unique Resource IDs, and no more than 10,000 resources. Preview makes no database changes. It reports read-only observations of internal resources under the Cask `content` root, separating present, missing, and unverified paths. Recovery accepts only a manifest at the configured Cask root, and only if that Cask is absent from SQLite. Each Cask import runs in one SQLite transaction, so parse errors or conflicts leave that Cask unchanged.

`scan` discovers at most 1,000 immediate UUID-named Cask directories under configured storage and validates every manifest before `recover-all` begins. `recover-all` skips existing Casks, so an I/O failure after an earlier Cask commits can be retried. It never rewrites an existing Cask. The observed filesystem state is reported for inspection but does not restore ownership or cleanup authority.

Recovered Casks enter `RECOVERY_REQUIRED`. Recovered Resources have unknown availability, referenced management, external containment, and `DETACH_ONLY` associations. This intentionally drops claimed ownership even if the manifest says `MANAGED`. Several manifests can re-associate the same Resource ID when its kind, name, and path agree; conflicting records fail the transaction. The hash detects corruption; it does not make a manifest trustworthy. Current filesystem reality and ownership must be verified separately before any future managed action. Valid custom categories are restored; unavailable category keys fall back to `other`.

## Scope and compatibility

The existing per-Cask version 1 recovery manifest remains the on-disk projection and is generated by retryable projection jobs. CLI and GUI expose shared inventory, report, preview, discovery, and recovery operations. Application-provider observations are deferred until the installation model arrives in Milestones 6–7; v0.1 Milestone 5 resources are filesystem items only.
